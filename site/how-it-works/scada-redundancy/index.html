How SCADA Server Redundancy Works

Set the heartbeat interval, the number of missed heartbeats before failover and the RTU poll cycle. Watch the primary server fail, the standby count the missed heartbeats, take over polling and the operator clients reconnect.

Live animationAdjustable slidersFormula and example

Quick answer: A redundant SCADA system runs two servers: the primary polls the RTUs and serves the operator clients, while a hot standby receives a live copy of its database. When the standby stops seeing the heartbeat for the set number of intervals, it becomes primary and starts polling.

What Is a SCADA Server Redundancy?

A SCADA server collects data from RTUs and PLCs across a pipeline, a water network or a substation and serves it to every operator screen. If that single server stops, operators lose their view of the whole system, so critical systems run a redundant pair.

The primary server does all the polling and writes to the real time database, alarm list and event log. It replicates every change to the standby over a dedicated link and both servers exchange a heartbeat at a fixed interval.

If the standby misses a set number of heartbeats in a row, it decides that the primary has failed and takes over. The settings for heartbeat interval and missed count are a balance between a fast failover and avoiding a false one on a busy network.

SCADA Server Redundancy Working Principle Step by Step

  1. Server A is primary: it polls every RTU in turn, updates the real time database and serves the operator clients.
  2. Every change in the database, alarm list and event log is replicated to Server B, and both servers send a heartbeat every interval.
  3. Server A fails; Server B stops receiving the heartbeat and counts the missed intervals.
  4. When the missed count reaches the set value, Server B becomes primary, starts polling the RTUs and the clients reconnect to it.
  5. After repair, Server A copies the database from Server B and returns as the hot standby; the roles are not switched back unless an engineer does it.

SCADA Server Redundancy Formula

Failure detection time: t d = N × t hb, where N is the number of missed heartbeats and t hb the heartbeat interval
Worst case data gap ≈ t d + t poll, because the new primary needs up to one poll cycle to refresh every RTU
Poll cycles affected = gap ÷ t poll, rounded up
The takeover time of the server software adds to this; take it from the supplier data or measure it in a failover test
Example: t hb 1 s, N 3, t poll 2 s: t d = 3 × 1 = 3 s, gap ≈ 3 + 2 = 5 s, 5 ÷ 2 = 2.5, so up to 3 poll cycles are affected

Main Parts of a SCADA Server Redundancy

PartWhat it does
Primary serverPolls the field, owns the real time database and serves the clients
Hot standby serverRuns the same software and receives every database change, ready to take over
Redundancy linkDedicated network path for replication and heartbeat, ideally doubled
Operator clientsScreens that connect to whichever server is primary and reconnect after a failover
RTUs with event buffersHold time stamped events during the gap so they can be collected by the new primary

Where a SCADA Server Redundancy Is Used

Oil and gas pipelinesKeeps the control room view of compressor and valve stations during a server fault.
Water and wastewater networksMonitors reservoirs, pumping stations and treatment plants without a blind period.
Electrical substationsKeeps breaker status, alarms and sequence of events data flowing to the control centre.
Server maintenanceAllows patching or replacing one server while the other keeps the system running.

Advantages

  • Operators keep their view of the field after a server failure
  • Servers can be patched and maintained one at a time
  • Event and alarm history is kept on both servers

Limitations

  • Doubles server hardware and licences
  • Short timeouts can cause false failovers on a loaded network
  • A failure of the shared network or the field communication is not covered by server redundancy

SCADA Server Redundancy Field Tips and Common Problems

  • Run the replication and heartbeat on their own link, not on the busy field or client network, so a traffic peak does not look like a failed server.
  • Do a planned failover test after every software upgrade and record the real time from failure to the first fresh value on the screens.
  • Enable time stamped event buffering in the RTUs so changes during the gap are collected and not lost.
  • Place the two servers in different rooms or buildings with separate power so one local event does not stop both.

Frequently Asked Questions

What is the difference between hot and cold standby?

A hot standby runs and receives live data all the time, so it can take over within seconds. A cold standby must be started and loaded first, so the outage is much longer.

Why not set the heartbeat timeout very short?

On a busy or slow network a few heartbeats can be delayed without any failure. A very short timeout would then make the standby take over by mistake and the two servers could both act as primary.

Is data lost during a SCADA failover?

Live values are not updated during the gap, but RTUs with event buffering keep time stamped changes and send them when the new primary polls. The historian may show a short gap in trends.

What is a split brain condition?

It is when both servers believe they are primary, usually because the redundancy link failed while both servers kept running. Good designs use a second link or an arbiter to avoid it.
